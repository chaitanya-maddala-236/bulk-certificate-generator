# Interview Guide

## 60-Second Explanation

This system exposes a FastAPI bulk certificate generation API. When a client submits a job, the API validates each recipient independently, stores the job and recipient records in PostgreSQL, and queues background processing through Redis and Celery. A worker generates PDFs using a single ReportLab template, saves them to local storage, and updates per-recipient status. Because each recipient is processed independently, one certificate failure does not stop the rest of the job. The client can poll job progress and retrieve successful certificates through the API.

## Demo Flow

1. Submit a job with 5 recipients.
2. Make one recipient invalid.
3. Show the API returns immediately with a job ID.
4. Start or show the Celery worker processing.
5. Open `GET /api/v1/jobs/{job_id}`.
6. Show `Total: 5`, `Valid: 4`, `Invalid: 1`, `Success: 4`, `Failed: 0`, `Progress: 100%`, `Status: COMPLETED_WITH_ERRORS`.
7. Download one generated PDF.
8. Run the failure-isolation test showing Alice and Charlie succeed while Bob fails.

## Questions and Strong Answers

### Why did you choose asynchronous processing?

PDF generation can be slow and may involve thousands of files. Async processing lets the API accept the request quickly and gives clients a durable progress endpoint.

### Why Celery instead of FastAPI BackgroundTasks?

FastAPI `BackgroundTasks` run inside the API process and are best for small follow-up tasks. Celery gives a real queue, dedicated workers, retry hooks, and a path to horizontal scaling.

### Why Redis?

Redis is simple to operate locally and is a common Celery broker. It keeps the architecture realistic without extra complexity.

### Why PostgreSQL?

Jobs and recipients are relational data. PostgreSQL gives transactions, indexes, UUID support, and JSONB for validation errors.

### How do you handle 10,000 recipients?

The current implementation enforces a configurable `MAX_RECIPIENTS` and processes recipients in configurable batches. For 10,000 recipients, I would raise the limit deliberately, tune batch size, scale workers, and consider chunk tasks if processing time becomes too high.

### What happens if one certificate generation fails?

That recipient is marked `FAILED`, the error is stored, counters are recalculated, and the worker continues processing the remaining recipients.

### What happens if the worker crashes?

Successful recipients are already committed and will not be regenerated by normal pending-only processing. A production system would add stale `PROCESSING` recovery and explicit retry policies.

### What happens if a job is submitted twice?

Today it creates two jobs. Idempotency keys are documented as a future enhancement because they require payload hashing and conflict behavior.

### How would you implement retries?

I would add a retry endpoint for failed recipients or job chunks, reset selected failed rows to `PENDING`, and enqueue processing again. Automatic retries should be conservative to avoid duplicate file writes.

### How would you move storage to S3?

Implement the existing `StorageService` protocol with S3 operations. Store object keys in `certificate_path`, use presigned URLs if direct client download is desired, and keep database metadata unchanged.

### How would you scale workers?

Run multiple Celery workers and eventually split one job into chunk tasks. For very large jobs, use chunk coordination and aggregate counters in the database.

### How would you prevent duplicate certificate generation?

Only process `PENDING` recipients, keep certificate numbers unique, and use atomic storage writes. At higher scale, add row-level locking or chunk ownership.

### How would you authenticate the API?

Add OAuth/JWT or API keys at the FastAPI dependency layer. Authorization would scope jobs to organizations or tenants.

### Why not store PDFs in the database?

Files are better stored in filesystem or object storage. The database remains fast for metadata, status, and queries.

### How does progress calculation work?

`processed_count = success_count + failure_count + invalid_recipients`. Progress is `processed_count / total_recipients * 100`, rounded to two decimals.

### How do you handle invalid input?

Job-level validation can reject the request. Recipient-level validation is isolated, so invalid recipients are stored as `INVALID` with errors and valid recipients still generate certificates.

### How would you handle a 1 million recipient job?

Use CSV/object upload, chunked ingestion, chunk tasks, object storage, worker autoscaling, metrics, dead-letter queues, and a more careful counter aggregation strategy.

### How would you add multiple certificate templates later?

Add a `templates` table and a template ID on jobs. Keep the `CertificateGenerator` interface and choose a renderer based on template metadata.

### How would you support CSV upload later?

Add an upload endpoint that stores the CSV, validates rows in a background ingestion task, and creates recipient rows in batches.

### How would you implement cancellation?

Add a `CANCEL_REQUESTED` or `CANCELLED` job status. Workers would check between batches and stop processing pending recipients.

### How would you add notifications?

Emit an event or enqueue a notification task when a job reaches a final state. Email or webhook delivery should be separate from certificate generation.
